## Unit tests

`apps/api/tests/unit/` mirrors the source tree and runs with no database and no network:
static analysis of Python and TypeScript fixtures (including the demo projects), the
assertion check (every refusal rule, both languages), prompt assembly and the mock model,
coverage parsing (coverage.py and Istanbul), pull request diff scoping, failure
explanations, the sandbox's pure logic (limit classification order, workspace path
checks, runner commands, request signing, reading outputs without following links),
each provider adapter's translation to and from its wire format, archive unpacking and GitHub client
errors, configuration guards, the in-process cache, sealing and storage, middleware, the
CLI, and the OpenAPI drift check.

## The integration harness

`tests/integration/conftest.py` serves the real API over HTTP from a background thread
and runs the real worker in another, against real Postgres, real Redis, the mock services
(model providers in four wire formats and a GitHub API serving the demo repositories) and
the real sandbox service (`sandbox-test` on port 5635), which runs every test in nsjail
exactly as in production. Nothing is faked between the API and the sandbox: imports are
analyzed, tests are generated by the deterministic model and checked, and runs execute.

Isolation: `TEST_DATABASE_URL` and `TEST_REDIS_URL` choose the database and Redis index;
the suite drops and recreates its database, refuses any database whose name lacks `test`,
and refuses non-local hosts unless `ALLOW_REMOTE_TEST_DB=true`. `make test-matrix` sets
`TEST_KEY_MODE` and `TEST_STORAGE` per combination, each with its own database.

## The sandbox suite

`apps/api/tests/sandbox/` runs only where nsjail is installed, so `make test-sandbox`
builds the `sandbox-test` target of the sandbox image and runs it with every capability
dropped, `no-new-privileges`, the sandbox seccomp profile, a read-only root, an exec tmpfs,
`--network none`, and the same pids, memory and CPU limits as the service, mounting
`apps/api` read-only. Every test goes through `Runs.execute_sync`, the code path the
service uses for every request. It covers:

- **Real projects**: the demo Python project's suite with real coverage.py coverage; a
  failing assertion with actual and expected values captured in the same run; the demo
  TypeScript project with Vitest and Istanbul coverage.
- **Isolation**: no network from Python or Node; nothing readable outside the workspace
  (`/etc/passwd`, `/opt/venv`, `/proc`, `/root`, another run's workspace), nothing
  writable outside it (`/usr`, the toolchain), no secret in the environment, uid 65534,
  reports replaced by symlinks never followed (the hostile probes in
  `tests/sandbox/hostile/`).
- **Limits**: CPU, wall clock, memory, output and processes in Python, CPU or wall clock
  and memory in TypeScript, each stopped and named; the sandbox still works after every
  limit; a workspace path cannot leave the box.

## Browser tests

`e2e/` (Playwright) signs in as the demo users and follows the primary journeys against
the seeded stack; `scripts/qa/` (Puppeteer) visits every page in both themes at desktop
and phone width. Both read the demo password from `deploy/compose/.env`.

## CI

`.github/workflows/checks.yml` runs on every push: sanitization; ruff, mypy and the unit
tests for the API and SDK; ESLint, `tsc` and Vitest for the web. The full pipeline
(integration with the real sandbox, the sandbox suite, security checks, Terraform,
multi-arch images, e2e and QA) is in `.github/workflows-full/`, opt-in for forks
([README](../../.github/workflows-full/README.md)).
